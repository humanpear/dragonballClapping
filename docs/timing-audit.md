## 실행에 영향을 주는 문제와 수정

1. PR의 `useEffect([screen, battle])`가 행동 선택 때도 전체 비트 길이로 `setTimeout`을 다시 등록했다. 예를 들어 1초 비트의 900ms 시점에 선택하면 다음 비트가 원래 시작 후 1000ms에서 1900ms로 밀린다. 콜백 지연도 누적됐고, 타이머 콜백보다 먼저 처리되는 늦은 입력이 직전 비트로 허용될 수 있었다.
2. `battleClock.ts`는 예약된 경계 시각을 기준으로 따라잡는다. 입력 처리도 먼저 실제 시각까지 진행하므로 마감 직전 1ms는 허용하고 마감 정각부터 거절한다. 입력은 타이머를 연장하지 않고, 이전 턴 화면에서 발생한 입력은 다음 턴에 적용하지 않는다. 숨겨진 탭은 시간을 멈추고 복귀 시 남은 구간을 유지한다.
3. `shared/timing.js`를 클라이언트와 서버가 직접 참조한다. 서버 빌드 산출물은 이 순수 ESM 파일을 사용하므로 서버 배포 시 저장소 루트의 `shared/`도 포함해야 한다. 두 환경의 턴별 길이와 30턴 전이를 교차 검증한다.
4. Beat1·2는 입력 및 준비 포즈, Beat3 시작은 입력 마감·행동·에너지 공개, Beat4 시작은 판정이다. 기존 문서의 'Beat3 종료까지 입력'은 실행 코드와 달랐으므로 문서를 실제 경계에 맞췄다.

## 현재 Sites의 효과음 검증

별도 사이트에서 박수는 Beat1·2에 한 번씩, 기합은 Beat3에 재생한다. 수정 전 660ms 기 모으기 소리는 300ms 비트보다 길고 Beat4에서 정지시키지 않아 판정 구간까지 이어질 수 있었다.

사이트에는 2초/최소 1초 설정과 함께 매 경계에서 음원 정지, 늦은 프레임의 샘플 오프셋, 다음 경계까지의 최대 재생 길이를 적용했다. 지난 박수는 따라 재생하지 않고 선택·음소거 해제·일시정지 해제로 소리를 반복하지 않는다. 효과음과 캐릭터 포즈는 같은 커밋된 게임 상태를 읽는다. 오늘 수정된 모바일 배치와 Beat2 확대는 유지했다. 이 PR에는 해당 사이트의 오디오/UI 구현을 복제하지 않았다.
